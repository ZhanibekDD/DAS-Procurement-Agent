# Архитектура DAS Снабжение

## Граница продукта

`DAS Снабжение` — отдельный сервис и отдельная база. Он может обращаться к общему
DAS Agent за извлечением данных и подготовкой текста, но не хранит закупочное состояние
в истории обычного чата.

```text
Браузер сотрудника
        │
        ▼
DAS Снабжение API ──────► Procurement SQLite/PostgreSQL
        │                         │
        ├────► DAS Agent          ├── поставщики и подтверждённая память цен
        │      (извлечение,       ├── проекты, разделы, лоты
        │       классификация)    ├── КП и нормализованные цены
        │                         └── согласования и аудит
        │
        ├────► Corporate Email Adapter (IMAP + SMTP)
        ├────► Supplier Discovery Adapter (после MVP)
        └────► Messenger Adapters (после email-пилота)
```

## Почему не обычный чат

- тендер живёт неделями и имеет строгие статусы;
- одни и те же поставщики участвуют в разных проектах;
- каждое отправленное сообщение должно быть проверяемым;
- коммерческие предложения требуют нормализации и версии;
- доступ к проектным разделам и ценам должен контролироваться ролями;
- финальное решение должно быть отделено от рекомендации модели.

## Роли

- **Инициатор** создаёт заявку и спецификацию;
- **Снабженец** выбирает поставщиков и ведёт переписку;
- **Технический эксперт** подтверждает соответствие характеристикам;
- **Финансы** проверяют НДС, оплату и бюджет;
- **Комиссия/руководитель** утверждает победителя;
- **Аудитор** имеет read-only доступ к истории.

## Статусы

```text
draft → approved_for_rfq → rfq_draft → rfq_approved → collecting_quotes
      → clarification → comparison_ready → awarded | cancelled
```

## Неизменяемые правила

1. Найденный в интернете поставщик не становится проверенным автоматически.
2. До первого контакта проверяются реквизиты, регион и канал связи.
3. Массовая рассылка требует одобрения и лимита получателей.
4. Несоответствующее или неполное КП не может занять первое место.
5. Рекомендация ИИ не является решением о закупке.
6. Секреты почты и мессенджеров хранятся только в серверном secret store.
7. Все изменения шаблонов, сообщений, КП и решений записываются в аудит.
8. Исторические цены сравниваются только при совпадении валюты и единицы измерения.
9. Извлечённая ИИ цена не участвует в аналитике до подтверждения сотрудником.
10. Найденная ИИ закупочная позиция не создаёт раздел или лот до ручного подтверждения.
11. Проектная ведомость является приоритетным источником; исторический счёт с
    несовпадающими размерами или количеством не становится текущим КП.
12. Кампания по лоту с назначенным региональным кластером принимает только
    поставщиков из того же кластера.
13. Каждая извлечённая позиция хранит документ, страницу и ссылку на строку
    спецификации.
14. Повторная IMAP-синхронизация не создаёт письмо повторно: уникальность задаёт
    `Message-ID`, а курсор UID хранится отдельно для каждого ящика.
15. Ответ поставщика связывается с лотом только по проверяемому коду `[RFQ-id]`
    или существующей цепочке `In-Reply-To`; произвольный текст не меняет закупку.
16. Вложение проверяется по размеру расширению и magic bytes до регистрации как
    документ. Заблокированный файл не открывается и не отправляется обратно.
17. SMTP принимает только согласованное сообщение. Отправка является отдельным
    действием сотрудника и по умолчанию выключена конфигурацией.

## Контур корпоративной почты

```text
Timeweb IMAP → Message-ID dedup → поставщик + RFQ → вложение в документы
                                                   ↓
Timeweb SMTP ← ручная отправка ← согласование ← черновик ответа
```

Пароль читается из server-side secret. HTML письма преобразуются в безопасный
текст и не вставляются в интерфейс как исполняемая разметка. Ошибка синхронизации
или SMTP сохраняется без секрета и отображается сотруднику.

## Контур разбора проекта

```text
Исходный проект → DAS AI/OCR → procurement_suggestions (needs_review)
                              → сотрудник проверяет объёмы и источник
                              → approve: раздел + лот в одной транзакции
                              → reject: причина сохраняется в аудите
```

Повторное подтверждение заблокировано. При ошибке создания лота вся транзакция
откатывается, поэтому частично созданного раздела или дублирующего лота не остаётся.

## Следующая техническая итерация

1. PostgreSQL и миграции Alembic вместо SQLite для многопользовательской production.
2. RBAC и SSO/Open WebUI identity bridge.
3. Объектное хранилище для проектов, счетов и КП.
4. Очередь задач для OCR, почты, поиска и напоминаний.
5. Парсер счетов и предложений с обязательным human review.
6. Версионирование тендерной таблицы и протокола выбора.
